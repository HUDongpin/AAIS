# AAIS

AAIS is a focused Cognitive Apprenticeship learning system with four product agents:

- `A1` Guide Agent for expert modeling, checks for understanding, and task release.
- `A2` Monitoring Agent for behavior monitoring and low-interruption coaching.
- `A3` Reflection Agent for articulation prompts and expert trace comparison.
- `A4` Scaffolding Agent for capped metacognitive support during practice.

Production AAIS is deployed on Vercel and uses Neon Postgres for learner-session persistence.

The enterprise gate runs lint, full TypeScript checking, unit tests, and a production build.
The enterprise verifier checks the deployed readiness endpoint and its production subchecks, including OIDC role-mapping readiness source names, security headers, `/terms` and `/privacy` legal pages, LRS read-only health, OIDC start flow, optional real OIDC callback plus learner-session handoff smoke, final SSO-only mode, and optional trial learning-session plus login-throttling smoke without printing secrets or cookies; readiness failures include redacted response diagnostics such as HTTP status, safe content type, JSON readability, and fixed failure category without storing the response body.
The release evidence verifier checks that the clean source-provenance, archived Vercel production environment preflight, Vercel deployment, OIDC config dry-run, live-AI, and Neon restore artifacts are present, fresh, from the same release candidate where applicable, mutually compatible, redacted, secret-scan clean, and passing, including real OIDC callback evidence, static legal-page evidence, the Vercel Cron outbox drain configuration, a redacted Vercel platform signal, enterprise smoke evidence generated after the latest Vercel env preflight and Vercel deployment READY inspect, source commit alignment with deployment evidence, and a deployed-model fingerprint match for the live AI evaluation.
The enterprise release check runner sequences the clean source-provenance check, Vercel env preflight, Vercel deployment READY inspect, deployed enterprise smoke, and final release evidence verifier in that order, then writes a small redacted gate summary whose pass/fail status follows the final release evidence report, including the scheduled Vercel Cron outbox drain evidence.
`npm run release:env-template` generates an owner-fillable private env template from the missing Vercel Production names plus a redacted report; it can prefill the non-secret `AAIS_RELEASE_ID`, while `<REQUIRED:...>` placeholders for Neon/OIDC values intentionally fail closed in `npm run provision:vercel-env` until replaced with real values.
`npm run verify:oidc-config` reads a local owner-provided env file transiently, validates the enterprise OIDC issuer/client/redirect shape, checks issuer discovery unless the full explicit endpoint set is supplied, fails closed on partial explicit endpoint overrides, and writes only redacted booleans, missing names, placeholder names, and safe status categories.
`npm run release:restore-template` generates an owner-fillable restored-Neon env template plus a redacted report; copy the template to `.env.postgres-restore.local`, fill the copy with the restored staging Neon URL, then `npm run verify:postgres-restore -- --env-file ./.env.postgres-restore.local` reads the restored database URL transiently and still emits only redacted evidence.
If the enterprise release check fails because owner-managed Vercel/Neon/OIDC values are absent or current production evidence is not traceable, `npm run release:handoff` generates a JSON and Markdown action list with variable names, granular redeploy reasons such as missing deployment git commit evidence, private env template paths, safe dry-run/apply command skeletons, transient OIDC callback placeholders, and local credential-file name inventory only; the inventory recognizes any accepted educator role mapping source name, and it never records secret values.
`npm run release:audit` turns the final gate and handoff into a 17-control readiness matrix, including deployed release identity, legal-page evidence, Vercel deployment READY evidence, and scheduled outbox drain, so remaining enterprise blockers are visible as pass/action-required rows without reading secret values.
`npm run release:bundle` creates a redacted evidence-bundle manifest with each artifact path, reported status, effective status, SHA-256 hash, and secret-scan issue name, including the OIDC config dry-run report; it exits non-zero while any required artifact is missing, action-required, or secret-scan failed.
`npm run release:refresh` runs the enterprise release check, private env template generation, restored-Neon template generation, OIDC config dry-run, Vercel env provision dry-run, handoff, readiness audit, and evidence bundle in sequence so all release artifacts and owner-action inputs are refreshed from the same current state; `--deployment-git-commit <git-sha>` is carried into the enterprise release gate, private env template, and Vercel provision dry-run for `AAIS_DEPLOYMENT_GIT_COMMIT_SHA`, the readiness audit includes scheduled outbox drain as a release control, and the command exits non-zero until the full enterprise gate is ready.

## Current Enterprise Status

Implemented:

- Signed HttpOnly app sessions.
- Production readiness fails closed when trial accounts are absent or invalid while trial login remains enabled, and supports SSO-only production when trial login is disabled.
- Enterprise release verification can require SSO-only mode, proving the login page exposes SSO, hides the trial form, and `/api/auth/app-session` refuses trial login without setting a session cookie.
- Actor-bound CSRF tokens for state-changing learner APIs.
- Learning APIs derive learner identity from the signed session instead of spoofable `studentId` fields.
- Learner sessions can use Neon Postgres through `AAIS_DATABASE_URL`, or through Vercel/Neon-provided `DATABASE_URL`, `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`, raw `PGHOST`/`PGUSER`/`PGDATABASE`/`PGPASSWORD` pieces, or legacy `POSTGRES_HOST`/`POSTGRES_USER`/`POSTGRES_DATABASE`/`POSTGRES_PASSWORD` pieces; file storage remains for development.
- Production learner-session APIs fail closed with `503` when no Postgres configuration is available, so Vercel deployments do not silently persist learning data to ephemeral file storage.
- Postgres restore rehearsal verifies a restored Neon staging database schema plus smoke write/read/delete without exposing database URLs.
- Final release evidence verification consolidates the Vercel production environment preflight, enterprise smoke, live-AI evaluation, Postgres restore reports, and Vercel Cron configuration before release sign-off, including Vercel deployment URL, redacted Vercel platform signal, traceable deployment git commit evidence, Neon provider identity, deployed `AAIS_RELEASE_ID` identity, static `/terms` and `/privacy` evidence, LRS outbox drain schedule evidence, freshness, secret scanning, provider/evaluation-version compatibility, and deployed-model fingerprint compatibility.
- LRS health GET remains a redacted read-only probe; smoke POST requires a signed session.
- LRS mirroring uses the AAIS product event language (`session_id`, `phase`, `task`, `agent`, `event`, `detail`) and adds xAPI context extensions for event family, evidence kind, cohort, role, and course id.
- LRS actor identity is pseudonymous; raw learner ids, prompts, artifacts, self reports, cookies, tokens, and secrets are excluded or redacted from xAPI detail extensions.
- Learner-session writes remain the source-of-truth fast path; with Postgres/Neon storage, LRS delivery is first written to a persistent `aais_lrs_outbox` table and then flushed asynchronously in batches with retry/dead-letter state, while local development can still use the in-process queue.
- `/api/learning/lrs/health` and `/api/system/readiness` expose redacted persistent outbox metrics (`pending`, `retry`, `sent`, `deadLetter`, `total`) plus the artifact/edit/planning coalescing policy so operations can see backlog and high-frequency-event controls without inspecting raw event payloads.
- `GET /api/learning/lrs/outbox/flush` is configured in `vercel.json` as a daily Vercel Cron safety drain and requires `CRON_SECRET` bearer auth; `POST` drains the same persistent outbox for administrator sessions with actor-bound CSRF, or for scheduled/operator calls when `AAIS_LRS_OUTBOX_FLUSH_TOKEN` or `CRON_SECRET` is supplied as a bearer token. Responses expose status, sent/failed counts, batch count, and redaction markers only.
- Rapid artifact autosaves are debounced in the learner UI, flushed when the learner leaves the editor, and coalesced again in the LRS outbox so high-frequency typing updates the latest `artifact_edited`, `artifact_saved`, and `planning_submitted` facts instead of flooding the API or LRS.
- A2 monitoring now emits low-interruption `monitoring_pause_detected`, `coaching_push`, and keyed `ai_acceptance_recorded` evidence from real learner behavior signals; duplicate clicks on the same AI reply are idempotent, decision revisions are explicit, and AI acceptance decisions count as AI interaction evidence without storing learner rationale text or raw message ids.
- `/dashboard` renders a teacher/admin-only cohort dashboard backed by `/api/learning/analytics?scope=cohort`, with safe phase/agent/event filters, CSV/JSON cohort export, pseudonymous learner rows, A2 coaching signals, AI acceptance/interaction counts, reflection status, deterministic risk bands, and LMS/HRIS/BI join keys without exposing secrets or raw learner text.
- `/api/learning/analytics` returns signed-session learner analytics, and `?scope=cohort` returns teacher/admin-only pseudonymous cohort analytics for dashboards and BI/LMS/HRIS joins without exposing secrets or raw learner text. Cohort analytics includes cohort `riskBreakdown`, learner `riskLevel`, stable `priorityReasons`, and `aiAcceptanceDecisions`, and also accepts safe join-key filters such as `phase`, `task`, `agent`, `event`, `cohort`, `role`, and `courseId` for scoped aggregate slices.
- `/api/learning/export?scope=cohort` gives teacher/admin sessions the same pseudonymous cohort slice as CSV or JSON for controlled BI handoff. It exports learner keys, risk bands, priority reasons, counts, reflection status, and safe session keys only; raw artifacts, self-reports, prompts, cookies, tokens, and secrets stay out of the file. CSV fields are escaped defensively so spreadsheet imports cannot execute formula-like values.
- Structured redacted audit events for login success and failure.
- Login consent links resolve to static `/terms` and `/privacy` pages that document responsible use, SSO/account boundaries, LRS/xAPI data handling, pseudonymous analytics, and controlled exports.
- Trial-account login throttling blocks repeated failed attempts by account and client address.
- Governed AI provider boundary with deterministic local fallback and optional OpenAI-compatible HTTP provider.
- Production live-AI gate requiring evaluation approval plus output guardrails that block secret-like provider content.
- Production readiness requires a verified live-AI evaluation manifest with zero blocked samples when external AI is enabled.
- Enterprise OIDC SSO boundary with signed state, nonce verification, PKCE S256, JWKS-backed ID token validation, configured teacher/admin role mapping, and AAIS session handoff.
- File-backed learner-session backup/restore helpers with checksum verification.
- Redacted production readiness endpoint at `/api/system/readiness`, including Postgres schema/connectivity probe and Neon storage-provider metadata.
- Redacted enterprise release verifier at `npm run verify:enterprise`.
- Redacted Vercel environment preflight at `npm run verify:vercel-env`, checking required production variable names without reading values.
- Global HTTP security headers configured through Next headers.
- CI workflow and `npm run ci` gate.

## Security Notes

- `aais_session` is signed, HttpOnly, SameSite=Lax, and Secure in production.
- `aais_csrf` is a signed, actor-bound double-submit token. Client state-changing requests must send it as `x-aais-csrf`.
- Request `studentId` fields are not trusted by learner APIs; the server derives the actor from the signed session.
- Audit events are JSON lines emitted to server logs with sensitive key redaction.
- Repeated failed trial-account login attempts return `429` with a redacted body and `Retry-After`.
- Model-provider runtime metadata reports provider/model/attempt counts but omits secrets and raw prompts.
- Production will not be readiness-green for the OpenAI-compatible provider unless `AAIS_AI_EVAL_APPROVED=true`, `AAIS_AI_EVAL_VERSION` is set, and either `AAIS_AI_EVAL_MANIFEST_PATH` points to a passing manifest or `AAIS_AI_EVAL_MANIFEST_JSON` contains a redacted passing manifest for the same provider/model/version.
- Production learning-state APIs intentionally return `503` until a Neon/Postgres database source is configured; this protects learner traces from being written to transient Vercel filesystem storage.
- `npm run ai:evaluate -- --env-json-output <path>` also writes the same redacted manifest as one compact JSON line for `AAIS_AI_EVAL_MANIFEST_JSON`; it stores sample ids and guardrail summaries, not raw prompts, model replies, or provider secrets.
- `npm run verify:vercel-env -- --auth-mode sso-only --ai-mode live` checks that Vercel production has the required enterprise variable names for session signing, release identity (`AAIS_RELEASE_ID` plus non-secret `AAIS_DEPLOYMENT_GIT_COMMIT_SHA` for CLI deploy provenance), Neon storage, SSO-only mode, OIDC, educator OIDC role mapping, live AI approval, and LRS; for Neon storage it accepts `AAIS_DATABASE_URL`, `DATABASE_URL`, `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`, raw `PGHOST`/`PGUSER`/`PGDATABASE`/`PGPASSWORD` pieces, or legacy `POSTGRES_HOST`/`POSTGRES_USER`/`POSTGRES_DATABASE`/`POSTGRES_PASSWORD` pieces, for OIDC it requires issuer/client/secret/redirect and at least one role mapping source (`AAIS_OIDC_TEACHER_GROUPS`, `AAIS_OIDC_TEACHER_EMAILS`, `AAIS_OIDC_ADMIN_GROUPS`, or `AAIS_OIDC_ADMIN_EMAILS`), reports only names, never reads encrypted values, and emits a redacted `provisioningPlan` with safe `vercel env add <NAME> production` command skeletons for missing variables. `--ai-mode deterministic` is only for non-live-AI verification and is not sufficient for final enterprise evidence.
- `npm run verify:source-provenance -- --release-id <release-id>` fails closed unless the release source has a real git HEAD and clean worktree; it writes only the release id, branch, short git SHA, dirty-count totals, fixed error category, and redaction markers, never file names or secret values. Final release evidence also requires this short SHA to match the Vercel deployment git evidence.
- `npm run verify:oidc-config -- --env-file <private-env-file> --base-url <vercel-url>` validates local OIDC values before they are applied to Vercel: missing names, `<REQUIRED:...>` placeholders, non-HTTPS values, callback mismatch, partial explicit endpoint overrides, explicit endpoint validity, issuer discovery reachability, and teacher/admin role mapping presence/basic format are reported as redacted booleans/categories without printing issuer, client id, client secret, mapped emails, mapped groups, endpoint URLs, authorization codes, cookies, or tokens.
- `npm run release:env-template -- --vercel-env-report <redacted-vercel-env-report> --base-url <vercel-url> --release-id <release-id> --deployment-git-commit <git-sha>` writes an owner-fillable env template with the non-secret `AAIS_RELEASE_ID` and `AAIS_DEPLOYMENT_GIT_COMMIT_SHA` prefilled when provided and fail-closed `<REQUIRED:...>` placeholders for secret/provider values, plus a redacted JSON report. The template suggests the AAIS OIDC callback URL and canonical Neon `AAIS_DATABASE_URL`, but does not contain secret values.
- `npm run release:restore-template -- --postgres-restore-report <redacted-restore-report-path> --release-id <release-id>` writes an owner-fillable restored-Neon env template with a fail-closed `AAIS_RESTORE_DATABASE_URL=<REQUIRED:RESTORED_NEON_STAGING_DATABASE_URL>` placeholder plus a redacted JSON report. Copy the generated template to `.env.postgres-restore.local` and fill that ignored private file before running the restore rehearsal.
- `npm run provision:vercel-env -- --env-file ./.env.production.local --report <redacted-vercel-env-report> --release-id <release-id> --deployment-git-commit <git-sha>` dry-runs the missing variable names from the Vercel env preflight against a local owner-provided env file; add `--apply` only after the dry-run says `status: "ready"`. `--release-id` and `--deployment-git-commit` can satisfy the non-secret `AAIS_RELEASE_ID` and `AAIS_DEPLOYMENT_GIT_COMMIT_SHA` without requiring them in the private env file. For the Neon storage slot, the local env file may contain `AAIS_DATABASE_URL`, Vercel/Neon `DATABASE_URL`, `POSTGRES_URL`, `POSTGRES_PRISMA_URL`, `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`, raw `PGHOST` or `PGHOST_UNPOOLED` plus `PGUSER`, `PGDATABASE`, and `PGPASSWORD`, or legacy `POSTGRES_HOST` or `POSTGRES_HOST_NON_POOLING` plus `POSTGRES_USER`, `POSTGRES_DATABASE`, and `POSTGRES_PASSWORD`; if matching raw port or sslmode variables are present, the provisioner carries them along too. The provisioner writes whichever accepted source is present, reads values transiently, and sends them to `vercel env add` through stdin, but its report records only variable names, command skeletons, and statuses. After an apply report says `status: "applied"`, run `vercel deploy --prod -y --no-wait`, then `npm run verify:vercel-deployment -- --deployment-url <deployment-url> --release-id <release-id> --deployment-git-commit <git-sha> --output <redacted-vercel-deployment-report>` against the returned deployment URL, and regenerate the Vercel env, enterprise, and final release evidence reports from the fresh deployment.
- `npm run verify:vercel-deployment -- --deployment-url <deployment-url> --deployment-git-commit <git-sha>` runs `vercel inspect <deployment-url> --json` and writes only redacted deployment status evidence: normalized URL match, aliases, `READY` state, `production` target, short git SHA from Vercel inspect or the explicit non-secret commit argument, checked time, and secret-scan status. It never stores raw inspect output.
- `npm run verify:postgres-restore -- --env-file <private-restore-env-file> --database-provider neon` refuses to run against any configured production database source (`AAIS_DATABASE_URL`, Vercel/Neon URL aliases, or raw `PG*`/`POSTGRES_*` pieces) by default, rejects placeholder restore URLs, rejects provider labels that do not match the database URL host, and emits only a redacted Neon restore rehearsal report.
- `npm run verify:release-evidence -- --release-id <release-id> --source-provenance-report <redacted-source-provenance-report> --vercel-env-report <redacted-vercel-env-report> --vercel-deployment-report <redacted-vercel-deployment-report> --deployment-url <vercel-url> --deployment-platform vercel --database-provider neon` fails unless the source-provenance report proves a clean git HEAD for the same release id, the Vercel env report is passing for `Production`, `sso-only`, and `live`, the Vercel deployment inspect report proves the expected deployment URL is `READY`, production-targeted, and tied to the same git commit that deployed readiness reports, and the archived enterprise verifier report, AI evaluation manifest, Postgres restore rehearsal report, and local `vercel.json` Cron configuration are present, fresh where applicable, from the same `release.id`, from the expected Vercel deployment URL and platform signal, from the expected Neon restore provider, mutually compatible, passing, redacted, and free of secret-like raw content; it requires the source short SHA to match the Vercel deployment git evidence, deployed readiness to report the expected `AAIS_RELEASE_ID`, OIDC start to include complete authorization-code boolean evidence, `/terms` and `/privacy` to return redacted HTML/content-presence evidence, both readiness and LRS health to prove the LRS outbox is `persistent` on `postgres` with numeric redacted metrics and artifact coalescing enabled for `artifact_saved`/`artifact_edited`, `vercel.json` to configure a daily Cron for `/api/learning/lrs/outbox/flush`, `oidc-callback` to be `passed` with learner-session handoff evidence (`learningSessionStatus: 200` and `learningSessionReadable: true`), filtered teacher cohort analytics to be proven through a teacher/admin OIDC callback session with pseudonymous aggregate output, risk breakdown, learner risk levels, stable priority reasons, AI acceptance decision counts, a matching cohort export JSON proof, and no raw learner text, `sso-only-mode` to prove trial accounts are disabled, the login page exposes SSO without the trial form, and `/api/auth/app-session` no longer issues session cookies, trial learning-session and trial-login throttle checks to be `skipped` for final SSO-only evidence, and the AI manifest `evalVersion` plus model fingerprint must match deployed readiness.
- `npm run verify:enterprise-release -- --base-url <vercel-url> --release-id <release-id> --deployment-git-commit <git-sha> --ai-eval-manifest <manifest-path> --postgres-restore-report <restore-report-path> --deployment-platform vercel --database-provider neon` is the final one-command release gate; it re-runs the source-provenance check, Vercel env preflight, Vercel deployment `READY` verifier, deployed enterprise smoke, and final release evidence verifier so the evidence-order and deployment checks cannot read stale reports. Its summary records only statuses, output paths, missing variable names, and boolean evidence.
- `npm run release:handoff -- --release-check-report <redacted-enterprise-release-check> --vercel-env-report <redacted-vercel-env-report> --provision-report <redacted-provision-dry-run>` generates the owner/ops handoff after a failed gate. It reads local credential files only to detect variable names, not values, accepts any one of `AAIS_OIDC_TEACHER_GROUPS`, `AAIS_OIDC_TEACHER_EMAILS`, `AAIS_OIDC_ADMIN_GROUPS`, or `AAIS_OIDC_ADMIN_EMAILS` as local educator role-mapping inventory, and emits JSON plus optional Markdown with the missing Vercel Production names, private env template path, safe provision dry-run/apply skeletons, safe `vercel env add <NAME> production` skeletons, the required non-interactive `vercel deploy --prod -y --no-wait`, required `verify:vercel-deployment` READY check, Neon restore rehearsal command, real OIDC callback smoke command with fail-closed `<REQUIRED:TRANSIENT_...>` placeholders, the post-callback SSO-only cutover action, and final `verify:enterprise-release` rerun command.
- `npm run verify:enterprise` treats OIDC start as passing only when the provider redirect is a complete authorization-code request with `response_type=code`, `client_id`, `redirect_uri`, `state`, `nonce`, `code_challenge`, `code_challenge_method=S256`, and an `openid` scope; the report records booleans only, not raw OIDC parameter values or PKCE verifier values.
- OIDC callback responses never store authorization codes or ID tokens in cookies.
- OIDC callback audit logs use fixed redacted failure categories, include only safe provider-mode and role-mapping source names, and clear the one-time `aais_oidc_state` cookie on both success and failure.
- `npm run verify:enterprise` can optionally smoke a real OIDC callback when supplied with transient callback URL and state cookie values; placeholder values fail locally and cannot count as evidence. Run this callback smoke before setting `AAIS_TRIAL_LOGIN_ENABLED=false`; after the callback it uses the returned session/csrf cookies to read `/api/learning/session`, proving SSO handoff and learner storage together while the report only records cookie attributes, HTTP status, and booleans.
- `/api/system/readiness` reports only status, missing variable groups, trial account count, storage probe state, storage provider/source env, OIDC configuration mode, OIDC role-mapping source variable names, AI provider mode, deployed release id, Vercel git short SHA when available, and redacted readiness metadata.
- `AAIS_TRIAL_LOGIN_ENABLED=false` disables the trial account form and trial login API while leaving OIDC login available; final enterprise evidence should run `npm run verify:enterprise -- --require-sso-only --release-id <release-id> --output <redacted-enterprise-report-path>`.
- `npm run verify:enterprise -- --output <path>` writes a redacted JSON report covering readiness plus required production subchecks, security headers, `/terms` and `/privacy` HTML/content presence, LRS read-only health, teacher/admin filtered cohort analytics plus cohort export JSON proof, OIDC start, optional trial learning-session access, and optional trial-login throttling; set `AAIS_VERIFY_TRIAL_ACCOUNT`, `AAIS_VERIFY_TRIAL_CORRECT_PASSWORD`, `AAIS_VERIFY_TRIAL_WRONG_PASSWORD`, and `AAIS_VERIFY_TRIAL_CLIENT_IP` only for staging smoke because the throttle check intentionally locks the account/client pair. For final SSO-only cohort evidence, capture the transient callback URL and matching state cookie from a teacher/admin OIDC login, then set `AAIS_VERIFY_OIDC_CALLBACK_URL`, `AAIS_VERIFY_OIDC_STATE_COOKIE`, and `AAIS_VERIFY_REQUIRE_COHORT_ANALYTICS=true`; the report records only HTTP status, booleans, and aggregate row counts.
- If an online enterprise smoke probe cannot reach the Vercel deployment, the report keeps raw errors omitted and records only a safe `errorCategory` enum such as `connect-timeout`, `response-timeout`, `dns`, `tls`, `network`, or `unknown`.
- Every route receives HSTS, content-type, frame, referrer, permissions, CSP, and cross-origin opener policy headers.
- See `docs/ops-runbook.md` for release, SSO, LRS, backup, and rollback checks.

## Learning Analytics And xAPI

AAIS treats the Learning Record Store as the learning-behavior fact layer. Server events use a fixed Cognitive Apprenticeship model:

- A1 records expert modeling, understanding checks, task release, and guided AI response completion.
- A2 records planning/artifact evidence, AI prompts, monitoring signals, AI acceptance, and low-interruption coaching.
- A3 records articulation, self-report, and student trace versus expert trace comparison.
- A4 records practice-stage scaffold requests and the fifth-request self-check transition.
- Platform events record session lifecycle, stage navigation, task selection, and task completion.

The learner summary at `/api/learning/analytics` focuses on teaching action: training-to-practice progress, scaffold dependency, reflection evidence, coaching/AI interaction signals, and integration join keys. Add `?scope=cohort` with a signed teacher/admin session for pseudonymous cohort totals, risk breakdown, learner risk levels, and learner rows; include safe join-key filters such as `phase=practice&agent=A2&event=coaching_push` when a teacher or later BI export needs a scoped aggregate slice. Use `/api/learning/export?scope=cohort&format=csv` or `format=json` for controlled downstream BI files after SSO authorization; CSV output uses spreadsheet-safe escaping for formula-like values. The `/dashboard` page presents the same cohort data as a teacher-facing action queue, including phase/agent/event filters and CSV/JSON export buttons wired to the same authorized APIs. LMS should remain responsible for course enrollment, HRIS for organization and roles, BI for aggregation, and AAIS for interaction traces plus A1-A4 agent evidence.
